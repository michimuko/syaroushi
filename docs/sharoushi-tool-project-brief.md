## 1. プロジェクトの背景と目的

- **目的**：副業としての収益化と、キャリアアップのためのポートフォリオ構築の両方を狙う
- **開発者の前提条件**：
  - 実装力：フロントエンド寄り、バックエンドは相対的に弱い → AIコーディング支援（Claude Code）を前提に設計
  - 稼働時間：週5〜15時間
  - 得意分野・業界知見：現時点では特になし（壁打ちを通じて社労士業界に着地）
  - 収益モデル：当初はこだわりなし。最終的にはSaaSサブスクリプション（月額制）を想定

## 2. 市場調査サマリー（ここまでの壁打ちの経緯）

### 2.1 なぜ「士業×中小企業のシステム化されていない領域」を狙うのか

日本の中小企業（約330万社超）はDXが遅れている業界が多く、業務用ツールは経費として支払われるため個人向けアプリよりも継続課金の単価・定着率が高い。特に「地味で技術者にとって魅力的に見えない業界（Boring Business）」は大手ベンダーの参入が薄く、個人開発者でも勝ちやすい構造がある。

### 2.2 検討した業界候補（比較検討の経緯）

| 業界 | 評価 |
|---|---|
| 士業（税理士・社労士・行政書士） | 経費で払われ支払意欲が高い。法定期限が明確で構造化しやすい → **採用** |
| 建設業（現場写真管理） | パイは大きい（許可業者約47万）が、ANDPAD等の大手が強く実装難度もやや高い |
| 賃貸管理会社（クレーム一元化） | ニーズは実在するが業界理解の一次情報収集にコストがかかる |
| 美容室・サロン（予約＋カルテ） | 競合過多のレッドオーシャン |
| 学習塾 | 比較サイトが乱立するほど競合ツールが多く、差別化が困難 |

### 2.3 士業内での大型ツール・競合の現況（重要：ここを踏まえて社労士に着地した）

**税理士向け**
- TKC／MJS（ミロク情報サービス）／NTTデータ達人シリーズ／freee会計／マネーフォワードクラウド会計
- TKCは「高機能だが操作が複雑」「TKC会員の税理士経由でしか導入不可」という不満あり
- **重要**：2026年7月13日、freeeが「freee顧問先管理」をリリース。法定納期限に基づく進捗管理（ガントチャート自動生成＋期限アラート）、資料回収リマインド、AIによる資料の自動仕分けを提供開始。ただしfreeeエコシステム（顧問先もfreeeユーザー前提）に依存する設計と見られ、他社会計ソフト利用先には効果が薄い可能性がある

**社労士向け（★今回の選定領域）**
- 社労夢（日本情報クリエイト、最大手）／オフィスステーション労務／SmartHR／給与奉行クラウド
- ITreview等のレビューサイトでもレビュー蓄積が少なく、クローズドな商流（営業経由での導入が中心）で一次情報が表に出にくい業界
- e-Gov電子申請のAPI仕様が最近になって本格公開されたばかりで、電子申請とソフトウェアの連携はまだ発展途上
- **「顧問先ごとの手続き進捗をガントチャート的に可視化する」機能は、freee顧問先管理や後述の許認可管理ツールに相当するものが見当たらなかった** → ここが狙い目と判断
- **【2026-08-15追記・一部修正】** 公式サイト（mks.jp/shalom/function/）を確認した結果、社労夢には**「手続進捗管理」という特許取得済み機能が実在する**。入社／退職／産休育休／高年齢雇用継続等のイベント単位で必要な申請手続きの進捗を管理し、提出期限日で色分け表示する機能を持つ。ただし「1つのイベント内での手続き進捗」なのか「事務所が担当する全顧問先を横断した一覧・ダッシュボード」なのかは公開情報からは確認できず、この点は引き続き未確定（無料トライアル等での一次確認を推奨）。**したがって「進捗管理機能そのものがない」という前提は修正が必要**。差別化の軸は機能の有無ではなく、「高機能・高コストな大型ツールに対して、軽量・低コストで顧問先横断ダッシュボードにすぐアクセスできるシンプルさ」に置き直すのが妥当（出典：[社労夢の機能](https://www.mks.jp/shalom/function/)）

**行政書士向け**
- 業界標準ツールが存在せず、gTOMO／クリックス／timsoft（事件簿管理）／俺の事件簿など小規模ベンダーが乱立
- 許認可期限管理には既に競合が存在：「行政書士HUB」（行政書士向け、月額2,980円〜、期限アラート）、「マルット」（事業者向け、月額11,000円〜、期限アラート＋AI自動書類作成＋要件チェック＋行政書士への代行依頼機能まで搭載）
- → 許認可管理は白地ではなくなっていたため、社労士領域にシフトした経緯がある

### 2.4 決定的な一次証拠：「社労士Tools」の存在

現役の社労士事務所（東京都杉並区）が、自事務所の業務効率化のために自作したWebアプリ・Excelマクロ・ブックマークレットを無料公開しているサイト（tool.shlc.jp）が存在する。プロが本業の傍らで自作ツールを作ってまで埋めようとしている空白があるということは、既存の大型ツールで満たされていない具体的なニーズの動かぬ証拠である。

確認できた具体的カテゴリと事例：
- **計算・試算系**：時間外労働時間計算ツール（原則・1か月単位変形制＝36協定の残業上限規制に関連）
- **テンプレート系**：年次有給休暇管理簿テンプレート（自動付与機能付き、一斉付与対応）
- **勤怠管理系**：勤務シフト表作成支援ツール
- **加工・変換系**：（詳細未確認。robots.txtの制約でクロールできず、サイト構造から存在のみ確認）

→ これらは「法改正のたびに更新が必要な計算ロジック」「Excelでは属人化・壊れやすい定型作業」であり、後述の差別化機能（5-D）に直結する。

**【2026-08-15追記】WebFetch/WebSearchでの確認結果**：以前の「robots.txtでクロール不可」という前提とは異なり、個別ページの取得自体は可能だった。確認できた具体的な計算ツール例：
- [時間外労働時間計算ツール（原則・1か月単位変形制）](https://tool.shlc.jp/jikangaikeisan/)：時間外・休日・深夜労働の時間数、および月60時間超過分を区分集計。ただし**月45時間／年360時間などの36協定上限に対する自動チェック・アラート機能は明記されていない**
- [年次有給休暇管理簿テンプレート（法定付与）](https://tool.shlc.jp/nenkyukanribo_houtei01/)：入社6ヶ月後＋以降1年ごとの法定付与に対応し、時効消滅・残日数をExcel関数で自動再計算。ただし**「時間単位付与・比例付与・分割付与には対応していません」と明記**されている
- [1年単位の変形労働時間制カレンダー作成ツール](https://tool.shlc.jp/1year_henkei/)：週52時間・1日10時間などの上限要件チェック機能を持つ

→ 見えてきた差別化余地：(1) 36協定の法定上限との自動照合・超過アラート、(2) パート・アルバイト等の**比例付与**への対応、(3) Excelダウンロード形式ではなく**タスク詳細画面から呼び出せる統合されたUI**。モジュールD（計算アシスタント）の正式な計算ロジック仕様化はPhase6着手時に確定するが、コンセプトの妥当性と大まかな差別化方向性はこれで確認できたため、実装着手前に必須だった「手動確認」のブロッカーは解消済み。

## 3. 選定したコンセプト

- **ターゲット**：社労士事務所（1〜数名規模の個人〜小規模事務所を主戦場とする）
- **コアバリュー**：顧問先ごとの法定手続き（算定基礎届、労働保険年度更新、36協定届、就業規則変更届、賞与支払届など）の進捗と期限を一元管理し、自動アラートで期限漏れを防ぐ
- **市場規模の目安**：社労士登録者数 約4.5万人、全国の社会保険・労働保険関連手続きが必要な事業所は270万社超
- **価格帯の想定**：月額3,000〜10,000円程度（顧問先数に応じた従量制も検討）

## 4. 「ツール非依存」の定義

社労士事務所の顧問先は、給与計算ソフトとして給与奉行、ジョブカン、freee人事労務、弥生給与、あるいはExcel・紙ベースなど、バラバラのツールを使っている。「ツール非依存」とは、本ツールが特定の給与計算ソフト・会計ソフトと連携必須にせず、あくまで**「進捗と期限を管理する上位レイヤー」として独立して機能する**という設計方針を指す。

これにより：
- 顧問先の環境を問わず即日導入できる（乗り換えコスト・導入障壁が低い）
- freee顧問先管理のような「自社エコシステム限定」の弱点を回避できる
- 将来的に主要な給与計算ソフトのCSVエクスポートを取り込む連携機能を追加することは可能だが、それは「あれば便利な拡張」であり「なければ使えない前提条件」にはしない

## 5. 簡単に真似できない差別化要因（今回の壁打ちで追加検討）

大型ツールや後発の模倣者が短期間では追いつきにくい機能を、以下の5点に整理した。いずれも「機能を追加するほど使いにくくなる」というリスクを避けるため、**コア機能とオプションモジュールを明確に分離**し、初期状態では最小限のUIのみを表示し、設定画面で個別にON/OFFできる構成とする（詳細は5章末尾の設計原則を参照）。

### A. Excel移行アシスタント（インポートウィザード）

士業事務所の多くが現在もExcelで顧問先・期限を管理している（前回までの調査で繰り返し確認された共通課題）。競合の大型ツール（社労夢等）に乗り換える最大の障壁は「ゼロから入力し直す手間」である。

- アップロードしたExcelファイルの列を解析し、「顧問先名」「期限日」「担当者」などの項目にAIで自動マッピングを提案 → ユーザーは確認・修正するだけで移行完了
- **逆方向のエクスポートも常に保証する**（CSV／XLSX）。ロックインの恐怖を取り除くことで導入ハードルを下げる
- 大手SIer製の硬直的なシステムでは後回しにされがちな部分であり、AIコーディング前提の開発者には実装しやすい領域

### B. 顧問先向け「進捗レポート」自動PDF生成

内部の管理画面だけでなく、社労士が顧問先に「今どこまで進んでいるか」を月次で報告できる、顧客向けの成果物を自動生成する。

- 顧問先ごとの手続き状況（完了／進行中／未着手）をワンクリックでPDF化
- 事務所ロゴ・所感コメントを差し込めるテンプレート機能
- 単なる内部管理ツールを超え、「顧客満足度向上・営業差別化ツール」としての価値を持たせる
- 出力：`laravel-dompdf`によるPDF生成。将来的にはブラウザ印刷用CSSでの簡易対応も可

### C. リアルタイム通知（Web Push／将来的にネイティブデスクトップ通知）

**ユーザーからの質問への回答**：現時点の設計（前回提示したロードマップのPhase 4・5）は「メール通知」「Slack／LINE通知（拡張）」のみを想定しており、**サイボウズデスクトップのようなOSネイティブのプッシュ通知は含まれていない**。つまり現状の設計のままだと、メールを見落とすかサイトを能動的に訪れない限り気づけない、というご指摘の通りの弱点がある。これは今回の差別化検討で解消する。

実現方法は2段階で提案する。

**Level 1：Web Push（PWA化）— まず実装すべきライン**
- フロントをPWA（Progressive Web App）化し、Service Worker + Web Push APIを利用
- Laravel側は `laravel-notification-channels/webpush` パッケージで対応可能
- ブラウザ（Chrome／Edge）さえ一度起動していれば、タブを閉じていてもWindows／Macの通知センターにOSネイティブのトースト通知が届く
- 別アプリのインストールが不要で、既存のLaravel＋Vue＋Inertia構成に無理なく組み込める
- 業務系SaaS（社労夢、オフィスステーション、行政書士HUB等）でここまで対応している例は限定的と見られ、実装できれば明確な差別化になる

**Level 2：常駐型デスクトップアプリ（将来の拡張候補）**
- Tauri（Electronより軽量、Rust製）で常駐トレイアプリを別途作成し、バックグラウンドでAPIをポーリングしてOSの通知センターに直接プッシュ
- サイボウズデスクトップに近い体験になるが、別リポジトリ・配布／自動アップデートの仕組みが必要になり開発対象が増える
- ポートフォリオとしての訴求力は高いが、MVPには含めず「本気で作り込んだ」ことを見せるための後続フェーズ候補とする

### D. 現場の“自作ツール”由来の計算アシスタント機能

「社労士Tools」の存在から確認できた、現場で繰り返し必要とされる計算ロジックをアプリ内に組み込み、Excelの「関数が壊れる」「毎年の法改正で更新が必要」という悩みを解消する。

- 時間外労働時間の上限規制チェック（36協定関連）
- 年次有給休暇の自動付与日数計算（一斉付与・入社日基準の両対応）
- 勤務シフト表作成支援
- 計算結果はタスクのメモ欄やカスタムフィールドに保存し、Bの顧問先向けレポートにもそのまま反映できるようにする
- **申し送り**：この機能群は「社労士Tools」の詳細な内容を実際に確認してから正式に要件化すること。今回はサイトの存在とカテゴリ構成までしか確認できていない

### E. カスタムフィールドによる汎用性確保

「どんな現場でも汎用的に使える」という要件を満たすため、`clients` テーブルと `procedure_tasks` テーブルに `custom_fields`（JSON型）カラムを追加する。事務所ごとに管理したい独自項目（管理番号、契約プラン、業界フラグなど）を、開発者による追加改修なしに設定画面から増やせるようにする。

### 機能過多を避けるための設計原則

1. **コア機能**（顧問先CRUD、手続きタスク管理、カレンダー、メール通知）と、**オプションモジュール**（A〜Eの差別化機能）を明確に分離する
2. 初期状態ではオプションモジュールは非表示。設定画面の「機能管理」から個別に有効化する方式にする
3. 1つの画面に詰め込みすぎず、モジュールごとに独立したメニュー項目として扱う
4. MVPで実装するのはコア機能＋C（Web Push）のみとし、A・B・D・Eは正式リリース後の拡張フェーズに回す（詳細はロードマップ参照）

## 6. 技術スタックと選定理由

| レイヤー | 技術 | 理由 |
|---|---|---|
| バックエンド | Laravel | Eloquent ORMによる高速なCRUD実装、Task Scheduling／Queue／Notificationが標準搭載され、期限アラートやバッチ生成の実装に直結 |
| フロントエンド | Vue 3（Composition API） | 開発者の得意領域を活かせる |
| 連携層 | Inertia.js | 別途REST/GraphQL APIを構築せずに、認証・ルーティングをLaravel側に一本化。開発工数をUI実装に集中できる |
| UI | Tailwind CSS（Laravel Breezeベース） | 最新のGUIを素早く組み上げられる |
| カレンダーUI | `@fullcalendar/vue3` | 月表示・週表示・色分け表示に対応 |
| PDF生成 | `laravel-dompdf` | 顧問先向けレポート生成（差別化機能B） |
| Push通知 | `laravel-notification-channels/webpush` | Web Push対応（差別化機能C） |
| 権限管理（将来） | `spatie/laravel-permission` | 事務所内の役割分担が複雑化した場合に備える |
| ファイル管理（将来） | `spatie/laravel-medialibrary` | 書類チェックリストのアップロード対応 |
| ファイルストレージ（将来） | S3互換オブジェクトストレージ（SSE必須） | 特定個人情報を含み得る書類の保存。非公開バケット＋署名付きURL（7.7章） |
| キュー監視 | `laravel/horizon` | 通知バッチの可視化。ポートフォリオとしての見せ場にもなる |
| テスト | `pestphp/pest` | 期限計算ロジック（法定手続きの周期計算）は単体テストで担保すべき重要ロジック |

## 7. DB設計（詳細版・今回の差別化機能を反映）

※マルチテナント方針（7.6章）に基づき、テナント配下の全テーブルに `office_id` を直接持たせる。以下の一覧では `office_id` の記載を省略せず明示する。

### offices（社労士事務所＝テナント）
id / name / contract_plan(仮, nullable) / timestamps

### users（事務所スタッフ）
id / **office_id(FK)** / name / email / password / role(enum: owner, staff) / timestamps

### clients（顧問先）
id / **office_id(FK)** / name / representative_name / address / phone / email / contract_start_date / status(enum: active, inactive) / assigned_user_id(FK) / notes / **custom_fields(json, nullable)** / timestamps

### procedure_types（手続き種別マスタ）
id / name / category / recurrence_type(enum: yearly, monthly, one_time, custom) / recurrence_rule(json) / default_lead_days(json, 例: [90,30,7]) / description / is_active / timestamps
※`office_id`を持たない**全事務所共有のグローバルマスタ**（7.6章参照）

### client_procedure_subscriptions（顧問先×手続き種別の紐付け）
id / **office_id(FK)** / client_id(FK) / procedure_type_id(FK) / is_active / lead_days_override(json, nullable) / timestamps
unique(client_id, procedure_type_id)

### procedure_tasks（個別タスクインスタンス）
id / **office_id(FK)** / client_id(FK) / procedure_type_id(FK) / title / due_date / status(enum: not_started, in_progress, documents_collected, submitted, completed) / assigned_user_id(FK, nullable) / completed_at(nullable) / notes / **custom_fields(json, nullable)** / **calc_result(json, nullable ※差別化機能Dの計算結果を保存)** / timestamps

### procedure_task_documents（書類チェックリスト）
id / **office_id(FK)** / procedure_task_id(FK) / name / is_required / is_collected / collected_at(nullable) / file_path(nullable) / **retention_years(int, nullable)** / **retention_until(date, nullable ※collected_at確定時に自動計算、7.7章)** / timestamps

### document_access_logs（書類の閲覧・ダウンロード記録、7.7章）
id / office_id(FK) / procedure_task_document_id(FK) / user_id(FK) / action(enum: view, download) / accessed_at

### notification_logs（送信済み通知の記録）
id / **office_id(FK)** / procedure_task_id(FK) / recipient_user_id(FK) / channel(enum: email, slack, line, webpush) / lead_days / sent_at

### push_subscriptions（差別化機能C：Web Push用）

## 7.5 権限モデル（ロール定義）

`users.role` は `owner`（所長・管理者）／`staff`（担当スタッフ）の2値。2026-08-15の要件定義で以下を確定。Laravel Policyの実装単位はここに合わせる。

| 対象 | 操作 | owner | staff | 備考 |
|---|---|---|---|---|
| 顧問先（clients） | 閲覧 | ○ | ○（全件） | 担当外も閲覧可（**確定**：小規模事務所では代理対応・電話対応の頻度が高いため） |
| 顧問先（clients） | 新規作成 | ○ | ○ | **確定** |
| 顧問先（clients） | 編集（基本情報・カスタムフィールド値） | ○ | ○ | 提案・要確認：作成可なら編集可が自然という前提。異論あれば要調整 |
| 顧問先（clients） | 削除 | ○ | × | **確定**：契約終了等の影響が大きいため owner 承認必須 |
| 顧問先カスタムフィールド | フィールド定義の追加・削除（モジュールE設定） | ○ | × | 提案・要確認：マスタ設定の一種としてowner限定 |

## 7.6 マルチテナント設計方針（2026-08-15確定）

**方針転換**：当初「v1は単一事務所前提」としていたが、複数の社労士事務所（互いに無関係な顧客企業）が同一システムを共有利用する**マルチテナントSaaS**を最初から前提に設計する。単一事務所限定の簡易実装は行わない（拡張性・保守性を優先する恒久方針、CLAUDE.md参照）。

### 採用方式：行レベル分離（共有DB + `office_id`によるテナント分離）

- テナント本体として `offices` テーブルを新設
- テナント配下の全テーブル（`users` / `clients` / `client_procedure_subscriptions` / `procedure_tasks` / `procedure_task_documents` / `notification_logs` / `push_subscriptions` / `client_reports`）に **`office_id`(FK, NOT NULL) を直接カラムとして持たせる**。親テーブル経由のJOINでの間接スコープには頼らない（クエリの安全性・速度を優先し、非正規化を許容する）
- `procedure_types`（法定手続きマスタ）のみ `office_id` を持たない**全事務所共有のグローバルマスタ**とする。算定基礎届・36協定届などの法定手続きルールは全国共通のため、法改正時に1箇所を直せば全事務所へ反映される。事務所ごとの調整は既存の `client_procedure_subscriptions.lead_days_override` で吸収する

### 安全性の担保：情報漏洩を構造的に防ぐ二重防御

1. **Eloquent Global Scope**：`office_id` を持つ全モデルは共通の `BelongsToOffice` トレイトを継承必須とし、Global Scopeで `where office_id = auth()->user()->office_id` を自動的に強制する。個別クエリでのWHERE書き忘れによる他事務所データの漏洩を構造的に防ぐ
2. **Policy層での二重チェック**：7.5章の権限モデル（Policyクラス）にも「対象レコードの`office_id`が自分の所属事務所と一致すること」を必ず組み込み、Global Scopeとの二重防御にする
3. **`office_id`はクライアント入力を信用しない**：常にモデルの`creating`イベントで認証ユーザーの`office_id`から自動セットする（フォームやAPIパラメータから受け取らない）
4. **専用テストの必須化**：「他事務所のデータには（URLを直接叩いても）一切アクセスできないこと」を検証するPestテストスイートを実装時に必ず用意する

### 採用しなかった方式とその理由

事務所ごとにDB/スキーマを物理分離する方式（`stancl/tenancy`等）は分離の堅牢性ではより高いが、事務所数の増加に比例してマイグレーション適用・バックアップ・DB接続管理の運用負荷が増える。開発者はバックエンド経験が浅く稼働時間も週5〜15時間であるため、現時点では運用が破綻するリスクの方が大きいと判断し不採用とした。ただし`office_id`によるスコープ設計は、将来「特定の大手事務所だけ専用DBに切り出したい」等の要件が出た場合にも土台として流用できる。

### 認証・ログイン方式

- v1ではサブドメイン等によるテナント振り分けは行わない。単一ドメインでログインし、ログイン後は `auth()->user()->office_id` から所属事務所が一意に決まる
- メールアドレスはプラットフォーム全体でユニーク（事務所をまたいだ重複は不可）とする。1人が複数事務所を兼務するケースは稀と想定しv1では非対応。将来必要になれば `(office_id, email)` の複合ユニーク制約への変更で対応可能

### 今後の実装への影響

- **Phase1**（`users`/`clients`CRUD）の時点で`offices`テーブルと`office_id`を含めたマイグレーションを書く。ここを後回しにしない
- 開発・シードデータとして最低1件の`offices`レコードを用意し、開発者自身の事務所として動作確認する
- 価格モデル・課金体系（企画書11章、未決定）は`offices`テーブルを起点に設計する（`contract_plan`等のカラムを想定済み）

## 7.7 個人情報・特定個人情報（マイナンバー）取扱い要件（2026-08-15確定）

### 法的背景

社労士事務所は顧問先従業員の個人情報を通常業務で扱うため、**個人情報保護法**に加えて**マイナンバー法（番号法）**の上乗せ規制（特定個人情報）を受ける。現行DB設計にマイナンバー専用カラムはなく、`procedure_task_documents`（書類チェックリスト）経由のファイルアップロードにのみ特定個人情報が入り得る構造。ここと、`custom_fields`/`notes`等の自由入力欄が主な対応対象になる。

### ファイルストレージ：クラウドストレージ＋サーバーサイド暗号化必須

- 本番運用はS3互換のオブジェクトストレージ（AWS S3等）を採用。**サーバーサイド暗号化（SSE）を必須**とする
- バケットは非公開（private）固定。直接公開URLは発行せず、**署名付きURL（一時URL、短い有効期限）でのみダウンロード可**とする（Laravelの`Storage::disk('s3')->temporaryUrl()`を利用）
- 開発中（Phase1〜4）はローカルディスクで進めてよいが、`procedure_task_documents`の実装に着手するPhase5より前にS3ディスクへ切り替える
- ダウンロード可否は7.5章の権限モデル（担当staff＋ownerのみ）にそのまま従う

### 保存期限管理：検知・通知は自動、削除は人が実行

- `procedure_task_documents`に `retention_years`(int, nullable) と `retention_until`(date, nullable) を追加。書類収集時（`collected_at`確定時）に、書類種別ごとの法定保存年数から`retention_until`を自動計算する
- 新規バッチ **`documents:notify-retention-expiry`**（毎日実行）：`retention_until`を過ぎた書類を検出し、ownerに通知する。**自動削除はしない**（誤って必要書類を消す事故を避けるため）。削除はダッシュボード等に表示される「保存期限切れ書類一覧」からownerが確認のうえ手動実行する
- 番号法が求める「不要になったら遅滞なく廃棄」の努力義務は、検知→通知→人の実行、という形で担保する

### アクセスログ：閲覧・ダウンロードの記録

特定個人情報の「取扱状況の把握」要件に対応するため、新テーブル `document_access_logs` を新設する。
id / office_id(FK) / procedure_task_document_id(FK) / user_id(FK) / action(enum: view, download) / accessed_at

### 自由入力欄への混入対策：検知して警告

- `clients.custom_fields` / `procedure_tasks.custom_fields` / `procedure_tasks.notes` への保存時、マイナンバーらしき文字列（12桁の数字、ハイフン区切り含む）を正規表現で検知し、フロント側で警告表示する
- **入力自体はブロックしない**（計算アシスタントの一時メモ等、正当な用途もあり得るため）。「マイナンバーは入力せず書類アップロードを使ってください」という警告に留める

### 今後の実装への影響

- Phase5（書類チェックリスト実装）着手前に、S3ディスク設定・署名付きURL・`retention_years`/`retention_until`・`document_access_logs`をまとめて実装する
- 7.6章のマルチテナント設計（`office_id`によるテナント分離）は、個人情報保護の観点からも必須要件だったことを再確認しておく

## 8. 主要バッチ処理（Laravel Scheduler）

- **`procedures:generate-upcoming`**（毎日実行）：`client_procedure_subscriptions` を走査し、周期ルールに基づき先読み期間内の `procedure_tasks` を自動生成。同時に `procedure_type` に紐づく書類テンプレートから `procedure_task_documents` を生成
- **`procedures:send-reminders`**（毎日実行）：期限との差分が通知ルールに一致するタスクを抽出し、`notification_logs` を確認しつつ重複なく通知（メール／Web Push／Slack／LINE）を送信
- **`documents:notify-retention-expiry`**（毎日実行）：`procedure_task_documents.retention_until`を過ぎた書類を検出し、ownerに通知（7.7章）
