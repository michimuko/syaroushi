# 実装時チェックリスト

新しい画面・フォーム・APIを実装するとき、または「実装できました」と報告する前に、このチェックリストで漏れがないか確認する。すべての項目が毎回必須というわけではないが、**該当しないと判断した場合もその理由を一言添える**（黙って飛ばさない）。

---

## 1. フォーム入力まわり

### Enterキーの挙動
- [ ] `<input>`内でEnterを押したときの挙動を意図的に決める（単一行フォームなら送信でよいことが多いが、**検索フォームで意図せず一覧が絞り込まれる／確認なしに削除処理が走る**、といった事故がないか確認する）
- [ ] `<textarea>`（メモ欄など）でEnterは改行として機能し、誤って送信されないこと（`@keydown.enter`をtextareaに仕込んでいないか確認）
- [ ] 複数の入力欄があるフォームで、Tab移動の順序が視覚的な並び順と一致していること

### 初期値・デフォルト値
- [ ] 新規作成フォームの初期値を明示的に決める（空文字なのか、業務的に妥当なデフォルトがあるか）
  - 例：`procedure_tasks.status` の初期値は `not_started`
  - 例：新規タスク作成時の `assigned_user_id` は「未割当」か「作成者自身」か、業務ルールを確認してから決める
- [ ] 日付系フィールドの初期値（今日の日付を入れるべきか、空欄にすべきか）を画面ごとに判断する
- [ ] enum/select系のデフォルト選択肢が「意味のある安全な値」になっていること（誤って危険な値がデフォルトにならないように。例：`client.status`のデフォルトは`active`）

### バリデーション
- [ ] フロント（フォーム側の簡易チェック）とバック（Laravel FormRequestでの厳密チェック）の**両方**で検証する。フロントだけの検証はAPI直叩きで簡単にバイパスされる
- [ ] エラーメッセージは「どの項目の何が問題か」が分かる文言にする（`The given data was invalid.`のような汎用メッセージだけで終わらせない）
- [ ] エラー表示位置は該当フィールドの直下に統一する（画面上部にまとめて出す方式と混在させない）
- [ ] 必須項目には視覚的なマーク（`*`等）をつける

### 二重送信・連打対策
- [ ] 送信ボタンはリクエスト中`disabled`にする（Inertiaの`useForm().processing`を使う）
- [ ] 削除・完了などの破壊的操作には確認ダイアログを挟む（特に`procedure_tasks`のステータスを`completed`に変更する操作、`clients`の削除など）

---

## 2. エラー処理

- [ ] APIエラー（4xx）はユーザーに分かる言葉で表示する。開発者向けのスタックトレースをそのまま画面に出さない
- [ ] サーバーエラー（500）発生時にユーザーが「何が起きたか」「次に何をすればいいか」分かるフォールバックUIを用意する
- [ ] ネットワーク切断・タイムアウト時の挙動を決める（無限ローディングのまま固まらないこと）
- [ ] 例外は握りつぶさずログに残す（`Log::error()`等）。特にバッチ処理（`procedures:generate-upcoming`、`procedures:send-reminders`）は失敗時に気づける仕組み（ログ＋できれば管理者への通知）が必須。夜間バッチが静かに失敗し続けるのが一番怖いパターン
- [ ] 通知送信（メール/Web Push）が失敗しても他の顧問先への送信処理全体が止まらないこと（1件の失敗でループを止めない）

---

## 3. 状態表示（ローディング／空／エラー／権限なし）

どの一覧・詳細画面も、最低限この4状態を意識する：

- [ ] **ローディング中**：スケルトンかスピナーを出す。一覧のちらつき（loading→データ表示の瞬間の空表示）に注意
- [ ] **データ0件**：「顧問先がまだ登録されていません」等、次のアクションに誘導する空状態を用意する（単に空白のテーブルを出さない）
- [ ] **エラー**：上記2章参照
- [ ] **権限なし**：`role: staff`のユーザーが管理者専用機能（手続き種別マスタ編集等）にアクセスしたときの挙動を決める（ボタン自体を隠すのか、押せるが403を返すのか。可能なら両方＝UIでも隠しつつバックエンドでも弾く）

## 4. データ整合性・セキュリティ

- [ ] **Mass Assignment対策**：モデルの`$fillable`（または`$guarded`）を明示し、FormRequestで許可したフィールドだけがDBに書き込まれること
- [ ] **認可（Policy）**：他の事務所スタッフが担当外の顧問先データを見られる/編集できる設計になっていないか（v1は単一事務所前提だが、`assigned_user_id`による閲覧範囲制限の要否は要件定義で確認する）
- [ ] **トランザクション**：複数テーブルにまたがる更新（例：`procedure_tasks`作成時に`procedure_task_documents`を同時生成）は`DB::transaction()`で囲み、途中失敗時に中途半端なレコードが残らないこと
- [ ] **N+1問題**：一覧系クエリで`with()`によるEager Loadingを使っているか確認する（`clients`一覧で`assigned_user`を都度クエリしていないか等）
- [ ] **排他制御**：同じタスクを複数スタッフが同時に編集するケースをどう扱うか（楽観ロック`updated_at`比較 or 単に「後勝ち」を許容するか）を意識的に決める。v1では後勝ちでも許容できるが、その判断をコメントか設計メモに残す
- [ ] **XSS**：Vueの`v-html`を使う箇所（顧問先メモ、レポートの所感コメント等リッチテキストになりうる項目）はサニタイズ方法を確認する
- [ ] **CSRF**：Inertia標準のCSRF保護がミドルウェアで有効になっていることを確認する（Laravel Breezeデフォルトで有効なはずだが、API的な使い方をする箇所がないか確認）
- [ ] **認証エラーの列挙攻撃対策**：ログイン等の認証フローで、「そのID/事業所コードが存在しない」場合と「資格情報（パスワード等）が誤っている」場合を、外部から区別できないようにする。エラーメッセージの文言だけでなく、**紐付けるフィールド名も統一する**（フロントでフィールドごとに別の場所にエラーが表示される設計だと、文言を揃えてもフィールド名が違うだけで判別できてしまう）。実例：`LoginRequest::authenticate()`で事業所コード不存在時も`login_id`フィールドに`auth.failed`と同じ文言で返すようにした（2026-08-22修正）
- [ ] **不要な内部情報のレスポンス露出**：モデルを`Inertia::render()`にそのまま渡す・`toArray()`する前に、フロントが実際には使わない内部専用カラム（S3等のストレージキー、内部ファイルパス、他ユーザーの`password`/`remember_token`等）が含まれていないか確認する。フロントが真偽値やIDしか必要としない場合は、生の値をそのまま渡さず`#[Hidden]`属性で隠した上でアクセサ（`Attribute::make(get: ...)`）を`$appends`で公開する。実例：`ProcedureTaskDocument.file_path`（内部ストレージキー、フロントは「ファイルがあるか」の真偽値しか使っていなかった）を`#[Hidden(['file_path'])]`にし、`has_file`アクセサに置き換えた（2026-08-22修正）

## 5. パフォーマンス・ページング

- [ ] 一覧系（タスク一覧、顧問先一覧）はページネーション（`paginate()`）を使い、全件取得しない
- [ ] カレンダービューなど期間指定で表示する画面は、表示期間に絞ったクエリにする（全タスクを毎回取得しない）
- [ ] Excel移行（大量データ）やPDF生成のような重い処理は同期処理でリクエストをブロックしない。件数が多くなりうる場合はQueueに逃がすことを検討する

---

## 6. 日付・期限計算まわり（このプロジェクト特有の重要ロジック）

- [ ] `procedure_types.recurrence_rule`から`due_date`を算出するロジックは、タイムゾーン（Asia/Tokyo固定でよいか）を明示する
- [ ] 「期限のN日前」（`default_lead_days`）の計算は閏年・月末日（2/29、31日→翌月なし等）のエッジケースを確認する
- [ ] この手のロジックは**必ずPestで単体テストを書く**（`.claude/skills/laravel-sail-commands`参照）。UIで目視確認しただけで終わらせない
