# UI/UXデザインガイドライン（Vue3 + Tailwind + Inertia）

社労士事務所スタッフが**毎日、長時間、業務として使う**管理画面という前提でのデザイン方針。派手さより「速い・迷わない・ミスらない」を優先する。数値の可視化・グラフを扱う場合はこのskillではなく`dataviz`スキルを使うこと。

---

## 1. 全体方針

- **データ密度優先**：一般消費者向けアプリのような大きな余白・大きなカードは避ける。1画面で多くの情報（顧問先数十件、タスク一覧）を一望できることを優先する。ただし詰め込みすぎて読みにくくならないよう、行間・区切り線でグルーピングする
- **一貫性 > 独自性**：同じ操作（削除、ステータス変更、絞り込み）は画面が変わっても同じ場所・同じ見た目にする
- **キーボード操作を軽視しない**：毎日使うツールなのでマウス操作だけに頼らない（検索欄への自動フォーカス、Escでモーダルを閉じる等）

## 2. Tailwindの使い方

- **spacingスケールを勝手に増やさない**：`p-3`,`p-4`,`p-6`のように既定スケールの中で統一する。`p-[13px]`のような任意値を多用しない
- **色は意味を持たせて固定する**（Tailwindのデフォルトパレットからプロジェクト内で用途を固定）：
  - ステータス色は`procedure_tasks.status`の値ごとに固定マッピングする（例：`not_started`=gray、`in_progress`=blue、`documents_collected`=indigo、`submitted`=amber、`completed`=green）。画面をまたいで同じ色を使う
  - 期限超過（overdue）は`red`系で統一し、他の警告色と混同しない
- **コンポーネント化**：同じ見た目のボタン・バッジ・カードが3箇所以上出てきたら、都度クラスを書かずにVueコンポーネント化する（`<StatusBadge>`, `<DueDateLabel>`等）
- ダークモード対応は本プロジェクトのMVPスコープ外（企画書に記載なし）。対応する場合は要件定義で明示的に合意してから着手する

## 3. テーブル・一覧画面

- ヘッダーは`sticky`にして、スクロールしても列名が見えるようにする（タスク一覧は件数が多くなる想定）
- ソート可能な列は矢印アイコンで状態を明示する
- 行クリックで詳細に飛ぶ場合、クリック可能であることが分かるホバー効果（`hover:bg-gray-50`等）を必ずつける
- フィルタ（ステータス／顧問先／担当者／期限範囲）は**常時表示**にする。業務ツールでフィルタが折りたたみメニューの奥にあると使われなくなる
- 空状態（0件）は「条件に一致するタスクがありません」＋フィルタリセットの導線を出す

## 4. フォーム

- ラベルは入力欄の**上**に置く（横並びラベルは長いラベル文言で崩れやすく、社労士業界特有の長い手続き名（例：「労働保険 概算・確定保険料申告書」）と相性が悪い）
- 1画面に詰め込みすぎない場合はセクションごとに区切り線＋見出しでグルーピングする（基本情報／連絡先／カスタムフィールド、など）
- 保存ボタンは常に画面下部の同じ位置に固定する。フォームが長くなる場合は下部に**追従（sticky footer）**させることを検討する
- 入力中の未保存離脱防止（Inertiaの`beforeunload`相当のガード）は、長いフォーム（顧問先登録・手続き種別マスタ編集）で検討する
- Enterキー挙動・初期値・バリデーション表示の詳細は`implementation-checklist`スキットを参照

## 5. モーダル・トースト・確認ダイアログ

- モーダルは「今のコンテキストを保ったまま素早く処理する」用途に限定する（削除確認、簡易な追加フォーム）。長いフォームをモーダルに詰め込まない
- 破壊的操作（削除、ステータスの後戻し）は確認ダイアログを必須にし、対象名を文言に含める（「顧問先『〇〇商事』を削除しますか？」のように、何を消すか明示する）
- 操作結果（保存成功、通知送信完了）はトースト通知で一瞬表示し、自動で消える形にする。モーダルで毎回「OK」を押させない

## 6. カレンダービュー（FullCalendar）

- ステータス別の色分けは3章の色マッピングと統一する
- 月表示がデフォルト。1顧問先あたりのタスク件数が多い事務所を想定し、日付セル内でのタスクの省略表示（+N件）と、クリックでの一覧展開を用意する
- 期限超過タスクは月をまたいでも視認性を落とさない（薄いグレーで過去日を沈めすぎない）

## 7. ダッシュボード

- 最重要指標（期限超過件数、7日以内、30日以内）は画面最上部・最も目立つ位置に固定する。これらの数値カードは色（赤・橙・青等）で緊急度を直感的に伝える
- 数値カードをクリックすると該当条件で絞り込んだタスク一覧に遷移する導線を必ず用意する（見るだけで終わらせない）
- グラフ・チャートで表現する場合は`dataviz`スキルのガイドに従う

## 8. アクセシビリティ最低ライン

- フォーム要素には`<label>`を必ず紐付ける（`for`/`id`）
- 色だけでステータスを区別しない（アイコンやテキストラベルも併記する。赤緑の区別が難しいユーザーへの配慮）
- モーダル表示中はフォーカスをモーダル内に閉じ込め、Escで閉じられるようにする
- クリック可能領域は最低44px四方を目安にする（特にモバイル/タブレットで顧問先訪問中に確認するケースを想定）

## 9. レスポンシブ

- 主戦場はPCのデスクトップ画面（事務所内での日常業務）。まずデスクトップレイアウトを作り込む
- ただし訪問先でタブレット/スマホから確認するケース（タスクのステータス確認・完了報告）は想定し、閲覧系画面（一覧・詳細・カレンダー）は最低限崩れないようにする。複雑な編集フォームまでモバイル最適化する必要はない（MVPでは）
